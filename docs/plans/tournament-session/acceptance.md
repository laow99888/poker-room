# 锦标赛连续牌桌：验收用例与交付证据

需求入口：[开发总说明](./README.md)。所有金额、身份与状态语义以 [数据与接口契约](./contracts.md) 为准。

## 1. 如何执行这份验收

每个用例记录 `ID / 测试层 / PASS或FAIL或未执行 / 命令或步骤 / 实际输出 / 证据路径`。未执行不是PASS。同一行为可以复用已有测试，但必须说明哪条实际执行的断言覆盖它。

测试分三层：

- 纯领域层：通过session模块公开接口操作状态，用独立预期核对金额/轮转/原子性；不直接把内部字段改成预期后声称操作通过。
- API/引擎层：实际调用prepare/view/advice并回放动作，验证身份、扣盲、行动顺序与错误码。涉及统计全部隔离临时_DATA。
- 浏览器层：真实DOM事件、真实模块与请求协调器；允许受控延迟/失败响应，但response结构来自真实接口。不能只调用与事件入口脱节的helper。

已有回归继续执行：核心采样、平分份额、分层EV、CFR金额、输入4xx、去重、HTML转义及异步保护。新增功能不能以放宽旧断言来获得全绿。

## 2. 固定验收数据

### F1：连续六人桌

- capacity=6；按顺时针seat1…seat6坐P1…P6。
- 每人10000，盲注100/200，anteEach=0；你=P5，seat5。
- 第1手BTN6/SB1/BB2，位置顺序seat1 SB、2 BB、3 UTG、4 HJ、5 CO、6 BTN。
- 开关learning=false，ICM关闭。
- 本手英雄牌AsAd；没有指定的其他牌不是真实观察。

### F2：无需摊牌即可确定的第一手结果

在F1依次录入seat3、4、5、6、1弃牌，seat2获池。

- 最终P1=9900，P2=10100，P3/P4/P5/P6=10000，总60000。
- 第2手BTN1/SB2/BB3，你seat5为HJ。
- 新手扣盲后P2剩10000，P3剩9800，P1仍9900；底池300。
- 这不是旧手SB再扣一次100、BB再扣一次200，必须按新身份与确认余额计算。

### F3：未知摊牌

F1中seat3/4/5弃牌，seat6跟注200，seat1弃牌，seat2过牌；公共牌2c3d7h/9c/Td，两名存活者逐街过牌。

- P1余额9900已知；P3/P4/P5=10000已知。
- P2/P6的真实最终余额未知；不得根据占位底牌把某一人标为真实获胜者。
- 人工填P2=9800、P6=10300，其余如上，总60000；这组数应可确认并接续。

### F4：单挑

capacity=6，仅seat2=P2与seat5=P5有筹码，你=P5。BTN/SB=seat5，BB=seat2；两人起始10000，100/200、无前注。

- 盲注后P5=9900、P2=9800，pot=300。
- 翻前P5先行动且call=100；P5跟注后P2可以过牌。
- 翻牌后P2先行动。
- 下一手角色互换，玩家余额不互换。

### F5：空庄位与空小盲（两个不同案例）

F5a：capacity6，seat6空，seat1…5入局，button6空，SB1/BB2。引擎5人，order=[1,2,3,4,5]；真实BTN徽标在空seat6，range_position的BTN在seat5仅用于范围估算。pot=300，翻前seat3先，翻后seat1先。

F5b：capacity6，seat1空，seat2…6入局，button6，SB=null，BB2。引擎5人，order=[2,3,4,5,6]；只扣seat2的200，pot=200。翻前seat3先，翻后seat2先。seat1既不发牌、也不收前注、也不进入ICM。

F5的具体现场位置由用户确认，本验收测试适配器对已确认输入的处理，不宣称程序应从任意淘汰历史自动猜出这组安排。

## 9. 必做浏览器连续操作脚本

### B-01 三手不中断主流程

1. 清测试专用浏览器上下文，按F1建桌，确认你seat5。
2. 第一手录F2，核对余额后下一手；检查你HJ及P1/P2金额。
3. 第二手人工结束，按上一确认余额填写全桌、保持总额，说明缺少后续动作；确认进入第三手。
4. 检查你UTG、BTN2；刷新，手数仍3、你的seat仍5。
5. 检查Network：默认关闭熟人功能，整个流程stats请求0。

### B-02 人员变化与单挑

1. 独立测试会话从3人开始，SB1/BB2/BTN3。
2. 手后seat1余额0，其余余额总和守恒；确认淘汰。
3. 预览并确认BB3、BTN/SB2，检查F4等价的扣盲与行动顺序。
4. 在实际选牌/动作点击下打完或手动结束下一手；再次换手应交换两位角色。

### B-03 慢响应与恢复

用受控延迟分别卡住view.json和advice.json，执行重录/撤销等长分支/设置下一手奖金；验证S-07…S-11。至少一次从真实DOM事件发起，不仅手工赋revision。

### B-04 手机布局和可操作性

在320、375、390、768、1440 CSS像素宽度各检查setup/playing/settling三态，至少检查6座、9座、两人带空位三种名单：

- 文档无非预期横向滚动；若表格局部滚动，容器与表头清楚，不把确认按钮挤出视口。
- 数字、角色和“你”不重叠；空位仍可选中；底牌/公共牌按钮支持触控。
- 结算余额输入不因每次render失焦或光标跳动；软键盘不遮住错误提示和提交入口。
- 图标按钮有标签；金额单位显式显示；disabled、加载、错误、无数据均可辨认。

只检测document.scrollWidth不等于完成上述视觉与点击验收。保存关键截图并实际打开确认内容，失败保存日志/trace。
