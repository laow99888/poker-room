# 算法可信度与性能方案

目标：说明程序算的是什么、检验它是否正确、在不降低质量的前提下缩短等待。当前没有足够证据给整体策略打“实战胜率分”或宣称达到多人 GTO 水平；第二版须以可复现的数学测试和性能报告交付。

## 1. 当前算法能力核对

| 模块与定位 | 当前作用 | 边界与必须修改的表达 |
|---|---|---|
| `equity.py::simulate` | 给定英雄牌、公共牌、对手加权范围的底池权益估算；部分固定牌局可穷举 | 结论以范围假设为条件；请求迭代数不必等于有效样本数 |
| `decision.py::advice_for` | 基于权益、底池赔率、位置范围、SPR 等构造行动建议 | 属于组合启发式，不是多人纳什策略求解器；不得显示“保证最优” |
| `cfr.py::solve_river` | 截断范围、离散下注尺度、分桶模型中的有限轮 CFR | 摊牌价值可精确，不等于完整德州博弈的精确解；改称“单挑河牌抽象策略参考” |
| `cfr.py::solve_street` | 翻牌/转牌抽样终局价值加抽象行动树 | 未完整求解未来街策略；不能沿用河牌的精确标签 |
| `textures.py::range_equity` | 范围对范围权益近似 | 合并多名对手范围不等于多人联合策略；暴露近似范围和有效样本 |
| `textures.py::nut_advantage` | 当前以两对以上组合占比构造代理指标 | 不是严格坚果优势；默认改名“强牌占比近似”，若保留原名须先重新定义并验证算法 |
| ICM 相关逻辑 | 使用手前筹码及奖金结构估算决赛桌奖金权益 | 只适用于输入包含全部剩余选手的场景；不等于已求得 ICM 最优行动 |
| 熟人画像 | 可按历史调整范围，默认关闭 | 关闭时不参与；基础范围不是已校准的个人对手模型 |

先修正命名、输出元数据和确定的正确性问题，再新增复杂策略。第一阶段不承诺完成九人完整 GTO 求解、自动预测对手真实牌、多人多桌实时 ICM 或根据少量个人输赢自动调参。

## 2. 质量档和结果契约

### 2.1 统一使用有效样本

建议默认质量档 `standard_v1`：主权益至少 **20000 个有效联合样本**。这是第二版设计值，不是当前前端既有事实。所有被用于主要金额 EV 的独立权益估算也必须达到该档要求；若复用同一批联合样本可直接计算多个边池，前提是概率语义已验证一致。

`iterations` 旧字段不可继续含糊地兼指尝试次数和有效次数。拒绝的牌组不计入有效样本；算法达到尝试上限、超时或用户取消时返回部分/失败状态，不能把请求次数写成有效次数。

主权益初始联合候选尝试上限为 `100 * requested_effective_samples`，同时受任务运行上限约束，以先到者为准；因此 standard_v1 最多尝试 2000000 个候选联合牌组。达到上限仍不足目标时输出 `sampling_exhausted`，不静默放宽对手范围。此上限是资源保护参数，可经压测调高，不能当作有效样本承诺。

RA、强牌占比及 CFR 采用各自的版本化参数，不把 CFR 的迭代次数等价为 Monte Carlo 样本数。初始不得低于当前对应场景参数：RA 当前约 1500–3000 次、强牌代理 12 个 runout、CFR 1600 次且 8 桶；实施前用基线测试固化调用处和求解器内部抽样参数。相同场景的质量变更必须明确改档和说明，不能把参数悄悄减半。

精确穷举例外：如果固定牌局剩余可能状态少于 20000，遍历全部合法状态是更强的结果，输出 `method=exact` 及真实穷举状态数，不重复样本凑到 20000。

所有参数由服务端质量档控制。普通用户不能通过旧 `iterations=1000000` 或修改请求体突破计算配额；若开放更高档，须由管理员配额决定，并明确展示其预期资源需求。

### 2.2 主结果示例

```json
{
  "job_id": "uuid",
  "hand_revision": 8,
  "decision_index": 11,
  "state_hash": "canonical-input-hash",
  "status": "completed",
  "quality_profile": "standard_v1",
  "engine_version": "build-id",
  "equity": {
    "method": "monte_carlo",
    "win_probability": 0.35,
    "tie_probability": 0.06,
    "lose_probability": 0.59,
    "pot_share": 0.38,
    "requested_effective_samples": 20000,
    "accepted_samples": 20000,
    "attempted_samples": 24860,
    "rejected_samples": 4860,
    "sampling_standard_error": 0.0032
  },
  "decision": {"kind": "heuristic", "available": true},
  "assumptions": {"estimated_stack_count": 2, "range_model": "position_preflop_v1"},
  "modules": {"cfr": {"status": "not_applicable", "reason": "multiway"}},
  "timing_ms": {"queue": 210, "compute": 8200},
  "seed": "recorded-seed",
  "stale": false
}
```

示例数值只说明结构，不是该项目任何实际牌局的计算结果。概率范围为 0–1，展示时才转百分比；`win + tie + lose = 1`（容许浮点误差）。多人平分时 `pot_share` 不是简单 `win + tie / 2`，必须按实际共享人数计入每个样本的份额。

`attempted_samples = accepted_samples + rejected_samples`，以完整候选联合牌组为单位计数；单名对手内部抽签尝试另设指标，不能混用分母。引擎版本、评估库版本、范围版本、采样器版本、种子、固定分块规则及各模块参数均可追溯。

采样误差按每个有效样本的底池份额 X（0–1）计算：标准误差为 `sqrt(sample_variance(X) / N)`；若展示近似置信区间，应说明只反映随机采样误差，不包含对手范围估错、筹码估算、行动模型和 ICM 假设的误差。不能把单纯赢牌二项式方差套给多人分池份额。

行动建议还需返回依据和适用标志，如 `estimated_stacks`、`partial_action_record`、`abstract_heads_up_tree`。筹码估算不阻断分析，但结果旁明确标明依赖估算；未知到无法形成合法局面时返回具体缺失字段。

## 3. 算法正确性工作包

### A. 手牌评估和规则

- 固定已知牌，用穷举验证河牌和转牌结果；覆盖同花顺、轮子顺、公共牌最大牌、多人平分、死牌和重复牌拒绝。
- 保持合法动作语义，特别是加到总额、最小加注、短码全下未重新开放加注权、未跟注下注返还、边池合资格玩家。
- 每个样本先按真实底池结构分配份额，再求 EV；不能把主池权益无差别套到所有边池。
- 评估器替换时，以确定牌型夹具、边界牌型及大批固定种子随机组合交叉验证。旧实现与新实现一致还不够，关键夹具必须有独立已知答案。

### B. 加权范围与联合采样

- 范围去除已知死牌、负权重及零权重非法输入；全部冲突时给明确错误，不得自动换成随机全部范围。
- 目标分布应写清为：各对手范围权重乘积，在互不重牌且不与已知牌冲突的联合牌组上重新归一化。
- 用极小可穷举范围计算精确联合概率，检验采样器；调换对手输入顺序不应系统性改变权益。
- 直接按顺序逐人过滤冲突再归一化抽牌通常会改变联合分布，不能以“没有重复牌了”为依据替换现有联合拒绝逻辑。
- 达不到有效样本目标时报告不可完成原因、有效数量与运行时间，不丢弃失败信息。

### C. CFR、范围指标及 ICM

- CFR 使用小型可枚举树验证行动概率和为 1、效用符号、到达概率、收益归一化、迭代收敛趋势；有限离散树的误差不能外推为完整游戏保证。
- 记录 `range_cap`、分桶、下注尺度及 runout 抽样对结果的影响，范围截断/映射可能造成误差必须显示。
- RA 与强牌代理给出独立公式和样例；不满足适用条件时 `not_applicable`，不能填 0 冒充结果。
- ICM 验证奖金总额守恒、单人极限、筹码对称性、零筹码排位边界和手前快照；不完整赛事选手集合时禁用该模块。

### D. 策略质量报告

构建固定、版本化的代表性决策集合：单挑/多人、短码/深码、翻前/各街、估算筹码、全下与多个边池。报告权益误差、行动合法率、建议稳定性、近似模块适用率和耗时。

不得仅用真实玩家几天的胜率证明算法更强，也不得因某次输牌就修改算法去迎合结果。策略建议如需评价 EV，要明确对手模型和参考求解范围；没有可靠参考的场景标“未验证策略质量”。

## 4. 性能改造顺序

### 4.1 先建立可复现基线

每份报告必须写：CPU 型号/实际 vCPU、内存、OS、Python 版本、依赖锁文件、评估后端、代码 commit、输入文件、种子、请求及有效样本、模块参数、冷/热缓存、并发数、耗时分位数和峰值内存。

之前开发机的探索记录中，9 人、请求 20000 次的完整建议约 49.2 秒；仅在临时实验中预计算范围抽样列表/累计权重后约 7.8 秒。该实验使用 treys，未作为正式改造提交；只是热点线索，不是这台 4C8G 服务器的 SLA，也没有证明两次均达到 20000 有效样本。实施者必须重跑带有效计数的基线，不能直接用这组数字报验收通过。

当前 `requirements.txt` 不含 eval7，存在 treys 回退路径。不得只看代码中的 try-import 就认定已经使用原生高速评估器。

### 4.2 低风险热点优化

1. 每个请求的合法范围组合、权重和累计权重只构造一次；不要在每次抽牌循环中重建相同列表。
2. 52 张牌的编码、牌掩码、不可变组合缓存复用；保持清晰的单位和评估器分值方向。
3. 批量评估合法候选牌组，减少 Python 小对象和逐样本函数调用；用 cProfile 等证据定位，不能先大面积重构。
4. 分别评估当前 Python 环境可安装的原生评估库；若需改变 Python 版本，独立验证 PokerKit/FastAPI 和所有现有回归。不能仅凭速度宣传直接替换。
5. 每个优化先保持同输入、同质量、同语义；若采样序列变化，以精确夹具和统计检验确认，不要求无意义的逐比特相等，也不能只比较一次四舍五入百分比。

改变采样器、评估器、联合范围语义分别提交和验证，方便定位误差来源。不得把质量修复导致有效样本增加的额外成本隐瞒为“优化无效”。

### 4.3 共享工作与缓存

同一联合样本可供多个权益输出复用，必须先明确全桌死牌和每个底池的边际分布。不能直接删去弃牌者/不参与某边池者的牌再认为概率等价。用小范围穷举比较共享算法与独立正确参考，通过后再减少重复计算。

缓存键至少包含 owner、手牌修订、决策点、英雄牌、公共牌、已知死牌、各对手范围及权重、行动历史和有效筹码、底池、盲注、ICM 参数、质量档、所有算法版本及种子策略。规范化序列化、稳定排序并散列，不用随意拼接字符串。

仅复用质量合格且输入相同的结果；低样本结果不能命中高质量请求。缓存按账户隔离，公共不可变牌表可全局共享。预计 TTL 10 分钟、结果缓存总内存初始 256 MiB，有上限和淘汰；历史分析档案存数据库，不随缓存淘汰而丢失。

### 4.4 渐进返回不等于减样本

可先返回满足 20000 有效样本的主权益，再返回完成的 RA/CFR 模块。界面显示“权益已完成，策略模块计算中”；整任务只有所有适用必需模块完成才为 completed，不适用模块明确给原因。

若提供更早的抽样进度，必须标明样本未满、不可当最终建议，不把临时 3000 样本结果伪装成同质量结果。分析等待期间实际牌局录入和余额保存继续可用。

## 5. 4C8G 的任务调度

### 5.1 进程与资源

初始生产布局：1 个 API 进程、1 个轻量调度进程、2 个持久 CPU 工作进程、1 个 PostgreSQL 实例及反向代理。调度进程和工作池只启动一套；禁止每个 API worker 各自创建 2 个子进程导致失控。

工作进程只计算不可变输入，不直接改实际牌局。调度进程领取数据库任务后提交固定进程池，负责租约、检查取消、保存检查点和结果。计算时不持有长数据库事务；不要把 CPU 重活放入 Web 请求的 BackgroundTasks 就宣称已隔离。

总计算并发默认 2。原生库内部线程默认 1，防止隐含的线程倍增。以压测观测整个服务内存，目标持续低于 6.5 GiB 且不持续 swap；超出时减少缓存/工作进程或扩容，不降低质量档来掩盖问题。

首版优先一任务一工作进程，提高多用户吞吐。只有空闲资源且经过验证时才支持单任务多进程分块；分块也必须计入全局 2 个计算槽，禁止子任务再创建嵌套池。FastAPI 多 worker 能提高请求承载，不自动让一手权益计算更快。

### 5.2 队列默认值

| 参数 | 初始值 | 行为 |
|---|---|---|
| 全局运行任务 | 2 | 整台服务器共享上限 |
| 全局等待任务 | 32 | 满时返回 429 + Retry-After，不无限积压 |
| 每用户运行 / 等待 | 1 / 1 | 同一决策重复请求合并；新决策替代过期等待任务 |
| 单任务运行上限 | 180 秒 | 不含排队；到时标 timed_out，保留部分结果但不称完整 |
| 等待有效期 | 300 秒 | 到时提示重新请求，避免旧局面占用未来算力 |
| 每用户默认日 CPU 预算 | 600 CPU 秒 | 配置起点，按实际进程 CPU 时间累计，管理员可调整 |
| 队列轮询 | 活跃时约 1 秒 | 可加退避，后台页降低频率；不为每用户建立忙循环 |
| 租约 / 心跳 | 15 秒 / 5 秒 | 过期领取受 attempt_id 保护，防旧工作者晚到覆盖 |

以上是保守初始配置，不是已验证容量承诺。配额日界按统一服务计费日 UTC 结算，界面显示下次重置的用户本地时间；不能通过修改账户时区重复获得配额。

同一用户较新真实局面到来时，旧计算设为 superseded，协作取消；另一项显式复盘任务不随无关牌桌操作无提示删除。实际开算前再次检查手牌版本及配额。用户之间按轮转选择最早有效任务，不能让同一账户连续提交饿死其他人。

被取消、失败和超时前已经消耗的 CPU 也计入预算；每次执行 attempt 只入账一次。正常完成从已持久化结果返回不再重复扣费。管理员页显示计算秒数和任务量，不需要暴露私人底牌。

每日预算在领取任务和每个计算检查点校验，并原子结算已消耗时间；达到上限终止本次剩余计算并标 `user_quota_exceeded`，保留部分结果的真实质量状态。允许最多一个检查批次的计量延迟，不允许每次重启任务重新获得完整预算。

### 5.3 状态、取消与崩溃恢复

任务状态：`queued -> running -> completed / failed / cancelled / timed_out / superseded`。`partial` 是结果完整度及进度标记，不是脱离生命周期的孤立状态；运行或超时任务均可附部分模块结果。

领取任务以短事务加行锁更新租约，可使用 `FOR UPDATE SKIP LOCKED`；每次执行生成 attempt_id。检查点和最终结果写回必须匹配有效 attempt_id，防止租约失效的旧计算覆盖新结果。

每个工作进程以有上界的小批次检查取消，目标取消响应 p95 不超过 2 秒；CFR、范围模块也要检查，不能只在主权益完成后检查。浏览器 AbortController 只取消网络等待，不能替代服务端取消。

重启后：已完成结果仍可查询；等待任务继续排队；运行中任务按租约过期恢复，最多自动重试 1 次且遵守总资源预算。恢复前检查是否已被新修订淘汰。若保存分块检查点，按 `(job_id, chunk_id)` 去重，种子由主种子和稳定 chunk_id 派生；重做同一块不能重复累加有效样本。

分块合并保存份额总和、平方和、胜平负计数和有效数，按有效数加权；不能直接平均各块的四舍五入百分比。若实现不能正确恢复随机状态/分块结果，明确从头重算并丢弃旧部分聚合，同时保留实际已用 CPU 计费，不假装无损续算。

前端接收结果时同时匹配 owner、hand_revision、decision_index 和 state_hash。过期结果保留在历史中但不放进当前行动建议；取消后晚到 completed 响应也不能覆盖当前视图。

### 5.4 容量如何解释

仅为理解吞吐的假设：若一项任务实际占用单工作进程 8 秒、同时运行 2 项，则理想上限约为每分钟 15 项。若无限接收 100 项同类任务，最后一批约 400 秒完成，还没计其他开销。本规格会先拒绝超出等待上限的任务，所以不会让所有请求静默等 400 秒。

真实 9 人 20000 有效样本的完整分析时长须在目标服务器测量；不引用上述 8 秒作为保证。100 人查看历史通常比 100 人同时跑分析容易得多。需要 100 人同时快速出完整结果时，应按测得的单任务 CPU 成本扩容计算节点或提升单核执行效率，不能靠 512 GB 磁盘解决。

## 6. 性能验收矩阵

固定输入至少覆盖：6 / 8 / 9 人，翻前 / 翻牌 / 转牌 / 河牌，宽范围 / 窄冲突范围，单挑 CFR，全下多边池，估算筹码，已知固定牌穷举。保存合法 fixture，不使用真实账户数据。

测试分为：

1. 单任务冷启动、热进程无结果缓存、缓存命中，分别报告，不把三种混为一组。
2. 1 / 2 个同时计算的稳态吞吐；5 / 20 项突发，观察排队公平性；100 项突发验证配额和队列满拒绝。
3. 1 / 5 / 20 / 100 个在线会话混合查询历史、保存动作和提交分析，记录 HTTP 延迟、数据库锁等待及内存。
4. 运行时修改手牌、取消任务、退出账户、关闭页面、杀死本任务测试工作进程、重启服务，验证不返回过期/跨账户结果。

必须分别输出排队时间、计算时间和端到端时间的 p50 / p95 / p99、通过任务数、429 数、有效样本、失败原因及质量档。每个固定场景至少 20 次正式测量；预热单独记录，不计入测量。

初始验收目标：在声明的在线混合负载下，排除真实网络传播的服务器端普通读写 API p95 < 500 ms、任务提交 p95 < 500 ms、取消 p95 < 2 s，队列不超过上限且不存在跨账户泄露。计算耗时需在阶段一冻结目标基线和优化目标；建议相同质量下最慢代表性场景热进程中位耗时至少降低 50%，不能以缓存命中代替单任务优化。

如果算法纠错改变了工作量，先给纠错后未优化的等质量基线，再比较优化版本；原始低有效样本结果仅作历史说明。目标不达成须报告实测容量和瓶颈并提出调整，不得改测试输入、样本数或验收数字伪装通过。

参考：[FastAPI 部署概念](https://fastapi.tiangolo.com/deployment/concepts/)、[服务器工作进程](https://fastapi.tiangolo.com/deployment/server-workers/)；这些机制说明不等同于本项目容量测试。
