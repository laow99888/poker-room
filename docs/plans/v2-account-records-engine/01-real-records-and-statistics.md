# 实战记录与统计契约

状态：待开发规格。本文中的 MUST 表示验收必须满足；不得用模拟输出补齐未知真实数据。

## 1. 四类对象必须分开

| 对象 | 含义 | 能否决定下一手实际余额 / 真实统计 |
|---|---|---|
| 现场观测 | 用户输入的实际筹码、实际动作、公开牌、真实名次 | 可以，但仍需判断完整性及是否能归因到该手 |
| 实战推导 | 从已确认起始余额和完整实际动作可确定的结果 | 可以；保留推导依据及依赖版本 |
| 建模假设 | 未知筹码估算、对手范围、假设行动、占位底牌 | 可以提供计算输入；不能标为已确认实际结果 |
| 分析结果 | 胜/平/负概率、底池权益、行动建议、CFR/ICM 输出 | 只供分析，不能写回实际输赢或自动淘汰玩家 |

赛事 `tournament` 属于一个账户；参赛次数 `entry` 属于赛事；牌桌会话 `table_session` 属于参赛次数；手牌 `hand` 属于一张牌桌。同桌入座者 `occupant` 不等于账户，也不等于 BTN / SB / BB。位置属于某一手的角色，不能作为玩家主键。

转桌创建新 `table_session`，保留同一 `entry`；重入创建新 `entry`；开始另一场锦标赛才创建新 `tournament`。对手再次入座使用新的入座 ID，避免旧座位历史错误归属。熟人画像不是维持座位身份的前提。

## 2. 筹码的数据语义

每个手前、手后余额使用以下结构。数据库可规范化存储；API 必须保留同等含义。

```json
{
  "occupant_id": "uuid",
  "model_chips": 9800,
  "actual_chips": null,
  "provenance": "estimated",
  "basis": "carry_forward",
  "source_observation_id": "uuid-or-null",
  "source_hand_revision_id": "uuid-or-null",
  "needs_review": true
}
```

- `model_chips`：计算使用的整数筹码。用于开始下一手的有效玩家必须大于 0；过程中全下可以为 0。
- `actual_chips`：已观测或可靠推导的真实余额，未知为 `null`；0 是明确数值，不代表未知。
- `provenance`：`observed`、`derived`、`estimated`、`unknown`。`unknown` 记录不能直接用于需要筹码的计算，须先录入显式估算；因此其 `model_chips` 可以是 `null`。
- `observed` 表示用户核对了现场值，不是程序证明没有录错。`derived` 必须有已确认的起点及完整实际动作/分池依据，否则降级为 `estimated`。
- `basis`：`manual`、`recorded_actions`、`carry_forward`，用于解释来源。沿用估算再减去盲注或下注后，来源依然为估算。
- 对于 `observed` / `derived`，`actual_chips == model_chips`，且 `needs_review == false`。估算和未知的 `actual_chips` 必须为 `null`。
- 金额存储为非负整数筹码。统一约束单个金额、底池和求和不超过 JavaScript 安全整数上限 `9007199254740991`；后端也验证，不仅依靠数据库 bigint。
- BB 只是显示和输入单位。使用该手冻结的大盲换算；不能因下一手升盲而改写上一手筹码。非整数换算须显示实际整数和舍入提示，确认后保存整数。

现有 `confirmedChips` 不能继续同时承担真实值和估算值。迁移后需明确分出建模数值和可信度；未能证明来源的旧数值默认标记 `legacy_unverified` 导入质量，并映射为估算，不假定已核实。

## 3. 最少输入的主流程

### 3.1 登录与开始比赛

首次注册成功即建立登录会话。默认页展示“继续当前比赛”和最近记录；没有记录时直接提供“开始比赛”。无需先填赛事名称、奖金和全部对手资料。

新比赛的必需输入沿用简化首屏：6 / 8 / 9 座、盲注、每人前注、我的筹码、当前庄位。默认所有座位有人，自己在 1 号物理座位并旋转到画面下方，其他人筹码按我的数值预填并明确标“估算”。赛事名自动以本地日期生成，可改名。只需要调整与默认不符的座位。

赛事名、奖金、买入、熟人功能、单独对手筹码在展开区域；禁止新增“逐个填写姓名后才可开始”的障碍。

### 3.2 记录当前手

三栏布局继续沿用，牌桌常驻赛事名、本桌第 N 手、我的位置、盲注和保存状态。显示桌容量与当前人数；全部有人的座位显示当前位置，不能只标 BTN / SB / BB。

动作输入使用合法动作范围；BB 优先时加注输入也使用 BB，附带筹码等值及“加到总额”的清晰含义。选择牌后立即显示选中态；分析异步执行，不能用等待分析锁住录入。

每次实际动作先更新本地待保存队列，再以版本控制保存服务器。刷新可恢复已保存动作；未同步部分明确提示“尚未同步”，不得显示“已保存”。断网可继续已有赛事的本地记录；恢复后需要冲突核对，禁止盲目覆盖另一设备。

英雄弃牌后仍记录后续动作。若现场来不及补齐，允许“直接核对结束余额”，填写原因并将 `action_coverage=partial`；这种手牌不能显示为完整回放，也不能据缺失动作生成确定的分池结果。无需编造动作或对手牌来结束一手。

### 3.3 手后核对

进入核对表时系统预填能够确认的余额：

1. 已确认手前余额且实际动作完整的弃牌者：预填手前余额减实际投入、加规则允许的返还。
2. 无摊牌获胜且动作完整：按真实动作分配底池和返还，预填结果。
3. 未知摊牌：相关选手结果待核对；不得使用引擎占位牌的赢家。
4. 起点是估算：即使动作完整，推导的结束值也仍是估算。
5. 摊牌牌面补齐：只有能决定各底池归属的全部合资格选手牌面都已知，才能据此确认分池。弃牌者底牌不必知道；部分获胜者亮牌不一定足以解决所有边池。

表格显示“手前筹码 / 预计结束值 / 实际结束值 / 状态”。确定行默认收起或排在后面；需要核对及发生变化的行优先显示，所有人均可展开修改。支持一次确认确定值，无须九行逐一点击。

用户有两种完成方式：

- **确认并下一手**：确认填写值；即便存在估算也可继续，但按钮旁须显示“X 人待核对”。服务端记录为 `settled_provisional`。
- **补齐后确认**：所有实际余额有可靠来源，记录为 `settled_confirmed`；这不自动意味着每个人的单手收益均可计算，仍需核对手前来源。

未知行可使用上次建模余额扣除已记录投入作为可编辑估算候选；必须标记“未含未知底池分配”，由用户明确接受。估算候选不允许由随机赢家生成。零余额候选不能直接把仍可能获胜的全下者移出下一手：用户需输入正的估算、确认实际淘汰，或暂不开始下一手。

本手所有参与者必须在结算记录中，包括即将离桌者。已确认的零余额可在提交摘要中勾选“确认淘汰”；输入过程中不能自动删座位。离桌但筹码为正是转出，不是淘汰。临时离开仍占座，按实际规则记录，不能当作出局。

### 3.4 总量核对与下一手

- 完全确认、完整动作、无筹码转入转出的手牌，总量应守恒。若不守恒，提示差额；用户须选择录入纠错等明确原因并二次确认，记录独立调整，不伪造赢家。
- 有估算值时，显示“估算总额，暂不能验证守恒”；不能用一个未知余额自动补平全桌。
- 先结算本手，再应用下一手人员变更；人员转入转出不记作该手输赢。
- 正常无人进出自动推进庄位一次。人员变化、空庄位或空盲位按现有预览要求核对位置。
- 升盲只作用于下一手。上一手的数额、位置和权益结果使用原快照。
- 所有结算提交使用幂等键和版本号；服务端事务成功才显示下一手完成保存。双击、重试、断网重发均不能推进两次。

## 4. 后补真实值：禁止制造虚假的单手收益

### 4.1 三种操作不能混为一谈

| 操作 | 入口与含义 | 对历史的影响 |
|---|---|---|
| 当前余额校准 | “现在实际有多少” | 从当前手间边界产生新的实测锚点；不会把差额分配给最后一手 |
| 历史记录纠错 | “第 12 手结束时实际是多少” | 生成第 12 手的新修订；计算依赖范围并展示影响预览 |
| 下一手人员变更 | 加入、转出、重入、淘汰 | 按人员事件保存；不混入上一手净输赢 |

示例：第 1 手前实测 10000，第 1 手后估算 12000，第 2 手后实测 9000。能够知道两手合计减少 1000，不能断言第 2 手输了 3000。第 1、2 手的单手净值暂不纳入“盈利手牌占比”。若之后核实第 1 手后实际 11000，则在动作和其他依赖一致时，两手分别为 +1000 和 -2000。

区间变化可以展示为“第 1–2 手累计变化 -1000，分手待核对”，不转换成多条假造的单手结果。

### 4.2 修订规则

每手保留不可变的手前快照、实际动作序列、牌面公开时间、手后观测和分析快照。修订追加版本，不覆盖旧版证据；历史视图默认读取当前有效版本，可查看修改原因和时间。

历史补正需进行以下步骤：

1. 预览受影响的后续手牌、统计、分析和当前余额，区分“仅更新已知事实”和“需要重建手前假设”。
2. 遇到独立实测余额锚点时，余额依赖在该边界停止；不能继续把较早差额加到该锚点之后。
3. 已冻结的后续手前快照不得静默改写。发现与新事实不一致时标记 `requires_reconciliation`，保留历史分析使用的原假设。
4. 最小版本可支持“修订该手事实 + 将受影响记录标待校准 + 从新实测锚点继续”。不能假装已经自动重算所有历史。
5. 可选的自动重建必须先生成独立预览，校验动作合法性、全下上限、边池和位置；用户确认后事务发布新版本。任何一步不合法都必须停止并定位手牌，不能裁剪下注量来通过。
6. 实际观测收益可以在可靠边界足够时重新计算；依赖过期或无法归因的统计排除。旧分析标为过期但保留查看入口；不自动批量重算消耗算力。

不能在进行中的手牌中直接修改起始筹码。需要纠正时保留当前草稿，回到手前边界修订并校验动作；或者把新观测应用到本手结束后的下一手，明确生效范围。

### 4.3 决策时的信息边界

底牌记录附 `revealed_at_action_index`，表示何时变为已知。事后摊牌可用于结果核对，但不能让旧时点分析自动“提前知道”对手底牌。复盘有“当时已知信息”和“加入事后信息”两种明确模式，后者属于假设分析，不覆盖历史原建议。

“假设他加注”“换一张公共牌”创建独立分析分支，不能修改实际动作、实际赢家、余额或统计。实际录入入口与假设分析入口明确区分；这不要求重做两套牌桌界面。

## 5. 统计定义：禁止只放一个含糊的胜率

所有统计返回 `included_count`、`excluded_count` 和排除原因，零分母显示“暂无已确认结果”，不能显示 0%。未记录到的比赛或手牌不推断为 0。

| 指标 | 定义 | 不可误用 |
|---|---|---|
| 已记录赛事数 | 已录入至少一手实际手牌的不同赛事数量 | 空草稿不计数；转桌和重入不新增赛事数 |
| 今日开始 / 今日结束赛事 | 按赛事实际开始 / 结束时间分别归属日期 | 不把跨午夜一场算两场新比赛 |
| 今日记录手数 | 实际手牌的 `played_at` 落入该日；包含暂定结果，另显示完整度 | 分析次数、保存次数、修订次数不算新手牌 |
| 盈利手牌占比 | 英雄可靠单手净筹码变化 > 0 的手数 / 所有可靠单手净值手数 | 分母包含净值为 0；估算、无法归因的校准差额及假设分支不纳入 |
| 拿池率（含分池） | 英雄获得至少一个实际底池份额的手数 / 实际拿池状态已知的手数 | 获得边池仍可能净亏损；不能用净值 > 0 等价替换 |
| 摊牌拿池率 | 上项再限定英雄实际参加摊牌 | 英雄已弃牌或摊牌结果未知不能混入分母 |
| 进圈率 / 冠军率 | 结果与奖金结构已确认赛事中的进圈 / 冠军赛事比例 | 筹码清零不必然等于已知名次；未结束赛事不进分母 |
| 当时底池权益 | 给定公开信息及范围假设的期望底池份额 | 是分析预测，不是个人历史赢牌率 |

“实际手牌”的计数起点为已保存至少一个现场实际动作，或已提交实际手后记录；仅点击建桌而自动创建的空手牌草稿不计数。盲注由界面默认生成但尚未确认开打，不单独构成已记录一手的证据。进行中的实际手牌可计入记录手数，结果覆盖率另算。

可靠单手净筹码变化 = 本手已确认结束余额 - 本手已确认开始余额 - 本手显式非牌局增加额 + 本手显式非牌局减少额。通常转桌和重入安排在手间，不存在手内增减。手内发现校准但归因不清时，直接判定单手净值不可计算，不为套用公式编造调整项。

对手估算不必阻止英雄统计：如果英雄自身两端余额和归因均可靠，其净值可统计；这与整手所有对手是否已确认是不同维度。手牌结果质量、动作完整度、英雄收益有效性必须分别保存。

拿池状态 `won_any_pot` 使用三态 `true / false / null`；只来源于明确实际分池、完整无摊牌过程或用户确认，不能从最终余额机械推断。用户只修改余额即可继续，不强迫其填写底牌或拿池标记；代价是某些统计暂时未知。

金额汇总分别按赛事展示。跨赛事 BB 变化使用每手自身的大盲归一化，并注明仅覆盖可靠记录；不把锦标赛筹码变动当作现金收益。ROI 只在同一币种、全部买入/重入费用及实际奖金完整时计算；跨币种不自动换算。

## 6. 日期、身份和统计修订

- 数据时间以 UTC 存储；账户时区默认 `Asia/Shanghai`。日统计使用该时区的 `[当日 00:00, 次日 00:00)`，禁止按服务器日期截断。
- 保存 `played_at` 与 `recorded_at` 两个时间；补录按实际发生时间归属，界面允许修正。修改时区后按新时区重新计算展示，原 UTC 时间不变。
- 每个账户统计只读取自己拥有的赛事、参赛及手牌。管理员权限不默认赋予浏览全部私人牌谱的能力。
- 本期可直接用数据库聚合有效版本，避免过早建立容易重复累计的统计缓存。如增加物化结果，须以版本化事件幂等更新并可全量重建。
- 历史删除使用可审计的软删除及恢复，默认统计排除已删除对象；永久删除需单独明确操作。账户禁用不等于删除历史。
- 同场重入：赛事数 1、参赛次数 2、相关费用计 2 次；首次出局并重入不能提前把整场赛事标为已结束。

## 7. 必须保持的界面行为

账户入口、赛事列表和管理员页独立于三栏牌桌；不让管理表格挤占牌桌。顶部提供保存状态和账户菜单，移动端保留当前手数、我的位置及关键行动。

待核对数量、队列状态、错误和过期结果使用可见文本加图标，不能只靠边框颜色。沿用项目已有图标体系，不使用 Emoji 代替按钮。按钮双击防重只是体验补充，服务端幂等才是数据保证。

断线重连、会话过期、另一设备修改、队列满、计算失败均有可恢复状态。重新登录后先核对账户身份和服务器版本，再恢复待保存草稿；禁止把 A 的草稿自动上传给 B。
