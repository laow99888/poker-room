# 第二版升级：账户、实战记录、算法可信度与计算性能

文档日期：2026-09-19。核对基线：`452eb8d`。状态：开发规格，尚未实施。

这里的“第二版 / R2”指产品升级，不等同于已有接口中的 `protocol_version: 2`。实现前必须重新检查 HEAD、工作区约定及现有测试。本目录是一个完整规格，不能只完成登录页面就宣布第二版完成。

## 1. 已确认需求与适用范围

| 编号 | 用户决定 | 实现要求 |
|---|---|---|
| R2-01 | 总管理员可控制是否开放注册 | 开放时注册成功即可使用，不设邀请码或人工审批；关闭时只禁止新注册 |
| R2-02 | 各账户有独立历史、每天场次和胜率统计 | 服务端持久化、逐资源鉴权、跨设备恢复；统计使用真实记录且展示有效样本数 |
| R2-03 | 主要用于锦标赛，每手连续记录 | 承接座位、庄位、盲注及筹码，允许淘汰、离桌和转桌 |
| R2-04 | 实际结果由用户掌握，不能用模拟赢家替代 | 真实结算和推演分开；实际余额决定下一手的真实基准 |
| R2-05 | 允许估算继续，之后补正 | 保留数值来源及估算依赖；估算不能伪装成实测结果或自动产生可靠收益 |
| R2-06 | 提高推演速度，不降低采样质量 | 消除热点、使用合适的计算实现、缓存、任务调度；不得暗中减样本或把部分结果标完成 |
| R2-07 | 使用规模 100 人以内；服务器 4C / 8 GB / 512 GB | 以 100 人以内在线规划；计算并发单独限流，实际吞吐以该服务器压测为准 |
| R2-08 | 延续已有上手简化及三栏界面 | 左参数、中牌桌与牌库、右操作和结果；当前模块高亮；手机纵向组织 |
| R2-09 | 熟人画像暂时不用，保留功能 | 默认关闭、退出主要布局；关闭时不读写画像，也不访问共享学习池 |

采用以下默认决策，不需要开发者再次向用户追问常规实现细节：

- “一场”暂按一次完整锦标赛定义；“一手”是单手牌；“转桌”是同场比赛下另一桌；重入是同场下新的参赛次数。用户没有单独确认“场”的定义，因此这是明确的产品假设。
- 云端账户模式必须登录。允许管理员关闭注册；初次部署默认关闭，由管理员显式打开。一旦打开，新用户无须审批。
- 默认用户名和密码登录，不把短信、邮件、社交登录作为第一阶段依赖。管理员可禁用账户、重置登录凭据、调整计算配额。
- 不自动识别现场、不代用户操作牌局、不建设多用户共同编辑同一桌。每人记录自己的赛事和桌况。
- 新建桌保留 6 / 8 / 9 座；比赛减员后内部继续支持 2–9 人，不要求另选“短桌产品”。
- 未知对手牌可以一直未知；允许只记录结果的手牌，但标明动作不完整，不能伪造完整复盘。
- 筹码不是现金。赛事奖金、买入费用可选；缺少完整费用和奖金时，不显示货币收益率。
- 本期保持“每人前注”语义。大盲前注 BBA 是独立规则扩展，未实现前必须明确显示不支持，不能把现场 BBA 金额直接写入每人 ante。

## 2. 先理解目前做到哪里

以下是代码事实，不是对旧功能的重新否定：

| 模块 | 当前事实 | 第二版改造重点 |
|---|---|---|
| `backend/table.py::settlement_preview` | 已区分无摊牌和未知摊牌；未知摊牌不直接承接占位牌产生的模拟收益 | 保留保护，加入来源、估算与补正链 |
| `frontend/session.js::validateSettlement` | 当前要求所有结束余额均为有效整数，不能保留未知值继续 | 加入显式的暂定结算，不得简单把空值改为 0 |
| `frontend/session.js::completeCommit` | 已有本地换手防重复、准备下一手与保存逻辑 | 迁入服务端事务并加入跨设备版本冲突控制 |
| `recentHands` | 浏览器中最多 100 手摘要；摘要不含完整动作和底牌 | 新手牌保存完整记录；旧摘要不能凭空恢复完整牌谱 |
| `backend/app.py::_player_id` | `X-Player-Id` 是匿名命名空间，不是身份认证 | 使用服务端会话识别账户，封闭旧接口绕过路径 |
| `backend/opponents.py` | JSON 存储并包含共享池 | 与个人历史存储分离；关闭画像时不使用，共享池不自动导入个人账户 |
| `backend/equity.py::simulate` | 蒙特卡洛存在拒绝采样；请求次数和有效次数并不总一致 | 用有效样本定义质量，报告尝试/拒绝/成功次数 |
| `frontend/app.js` | 当前 7 人及以上发 3000，其他发 5000 次请求 | 改成服务端版本化质量档，不能宣称现在界面统一 20000 次 |
| `backend/decision.py` | 权益、启发式行动、范围近似、可选 CFR/ICM 等组合 | 分别说明有效范围，不能当作完整多人 GTO 求解器 |

具体设计见后续文件。代码路径均相对于仓库根目录；函数名是定位依据，行号不作为稳定契约。

## 4. 推荐技术边界

保留 FastAPI、PokerKit、现有原生前端与测试方式。增加 PostgreSQL、SQLAlchemy、Alembic、成熟密码散列库和服务端会话；具体稳定依赖版本在实施第一阶段验证 Python / Windows 开发环境及 Linux 部署环境后固定。

部署起点为：反向代理 HTTPS + 单个 API 进程 + 独立计算调度进程及 2 个持久计算工作进程 + PostgreSQL。同一台 4C8G 机器上部署即可。第一期不引入 Redis、微服务集群或 Kubernetes。数据库任务表负责持久排队，不能只在 API 内存里保存任务。

100 人在线和 100 个高强度任务同时秒出结果不是同一要求。排队、取消过期任务和公平配额可以保护服务响应，但不会增加 CPU 算力。如果实际负载超过压测容量，应扩容或调整可用配额，不能隐瞒降低样本质量。

## 5. 交付结论

第二版应先建立可信记录与账户隔离，再优化计算热点和算法表达。最容易返工的不是登录页，而是把“补正估算余额”错误统计为“这一手真实输了多少”，以及把“请求 20000 次”误称为“有效采样 20000 次”。两者均列为上线阻断项。

本规格不承诺未经测试的策略优越性或服务器延迟。赛事现场能否使用电子辅助应以主办方规则为准；软件可计算不等于赛事允许使用。参见 [Poker TDA 官方规则](https://www.pokertda.com/view-poker-tda-rules/)。

直接交给开发执行者时，使用 [执行提示词](./04-delivery-and-acceptance.md#7-给-glm--zcode-的执行提示词)，要求其阅读全部文件后按阶段实施。
