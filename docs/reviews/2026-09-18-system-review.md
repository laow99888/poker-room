# poker-tools 系统性审查报告

审查日期：2026-09-18。基线提交：`b78bb73e044f9c140ff7f249af12db2d8ab239b8`。

## 结论

**综合评分：56 / 100。定位：有一定工程基础的学习原型，尚不适合作为可信的实战决策或真实牌谱复盘工具。**

最重要的风险不是界面精细度，而是部分合法或无效输入会让计算无法结束、策略计算的数学语义存在错误、学习记录链路实际失败，以及牌局回放混入系统虚构的对手底牌。现有测试全部通过，不能据此推断完整用户流程正确。

建议先修复下列 P1 问题，再增加功能或开展公开多人部署。无需整体重写或迁移前端框架；保留 PokerKit、FastAPI、原生前端，修正领域边界和接口契约更划算。

本报告按用户要求审查完整快照，而非某个提交区间。README 是产品承诺参考；没有外部正式规格。按规范/工程质量和产品/算法语义两条线独立检查，最终按“编号、问题、发生场景、交付方案”汇总。未修改业务代码、配置或用户统计数据。

## 项目理解

核心路径为：前端保存配置、手牌与动作列表 → `/api/hand/view` 用 PokerKit 从头回放 → 返回当前行动者、可操作金额、公共牌和结算 → 轮到英雄时调用 `/api/hand/advice` → 完成后调用 `/api/stats/record`。

建议路径为：行为分类 → 位置范围图 → 对手画像收窄 → 蒙特卡洛胜平负 → 底池赔率/SPR 与启发式混合建议 → 牌面结构、范围优势 → 单挑 CFR 参考。ICM 独立挂在牌局视图上，并没有参与行动 EV 或建议优化。

存储边界：前端 localStorage 保存设置/代号；后端所有访问者共享 `backend/data/opponents.json`；牌局本身靠请求中的完整动作列表回放。`run.py` 绑定本地地址，但仓库另有公开域名的 Nginx 反代配置，因此“本地单人使用”和“公开多人服务”需要分别评估。

优点：

- PokerKit 承担下注顺序、合法动作、边池分配等复杂状态机；treys 承担牌型评估，避免全部自研。
- 后端按牌桌、范围、权益、画像、CFR、ICM 分文件，结构直观；无状态回放天然适合复现。
- Kuhn、AKQ 和 ICM 暴力枚举对照是有价值的算法测试，CI 同时包含 Python 和前端检查。
- CFR 限制范围和迭代量、提供降级结果，并明确声明翻牌/转牌是终值近似，方向合理。
- 原生前端和本地静态资源适合小型离线工具，当前规模没有迁移 React 或引入微服务的必要。

## 关键证据与定位

以下为本轮实际执行或源代码直接确认的证据。模拟统计使用内存替身，没有写入真实 `opponents.json`。

### 01 范围循环

`backend/equity.py:174` 的 `while True` 没有失败出口，牌冲突仅重抽；`backend/ranges.py:52` 生成组合时没有统一点数字符大小写。独立进程调用 `simulate(['As','Ah'], [{'type':'range','text':'AA'}], ['Ad','Ac','Kd'], 1000, 42)` 超时；受控超时终止该复现进程。不能只增加重试次数：多家范围必须联合处理，否则后续范围无牌时仍会卡死或引入抽样偏差。

顺序偏差也已独立复现：英雄 KcKh，公共牌 5h7s9cJd3c；V1={AcAd,QcQd}，V2={AcKd,2h2d}。三个合法联合组合等权，英雄赢其中两个，精确胜率 66.67%。各运行10000次、seed=42，V1→V2 实测胜率 **49.98%**，V2→V1 为 **74.67%**。当前算法固定先选到的组合、只重抽后一家，会改变合法联合分布；应该整组拒绝冲突或显式计算条件权重。

### 02、03 CFR

定位：`backend/cfr.py:64`、`:99`、`:338`、`:355`、`:427`、`:443`、`:599`；上层剩余筹码来源 `backend/decision.py:54`。

复现代码：

```python
from backend.cfr import solve_river
from backend.ranges import expand_range

board = ['2c', '3d', '7h', '9c', 'Td']
r = solve_river(board, [('Ks', 'Kh')],
                expand_range('AA') + expand_range('QQ')[:4],
                pot_bb=2, to_call_bb=1, stack_bb=1.5,
                buckets=1, iterations=1600)
print(r['hero_strength'], r['avg_strategy'][(0, 0, '')])
# [-0.2], {'fold': 0.99999921875, 'call': 7.8125e-07}
# 40% equity, call EV = 0.4 * 2 - 0.6 * 1 = +0.2BB

r = solve_river(board, [('As', 'Ah')], [('Ks', 'Kh')],
                pot_bb=20, stack_bb=10, iterations=10)
print(r['root_labels'])
# ['check']
```

一桶案例用于隔离终值错误；同一取符号代码也用于默认多桶中包含混合结果的桶，不是“选择一桶导致的普通近似误差”。现有锚点常让每类手牌独立成桶，难以暴露该问题。翻牌/转牌不含未来行动的近似是已声明的设计限制，本报告未把这点本身当 bug。

默认 **8桶** 也已复现：board=5h7s9cJd3c、hero=KcKd；villain 取 `expand_range('QQ') + expand_range('TT')[:4]` 的10个较弱组合，以及 `expand_range('AA,JJ,99,77')` 过滤公共牌冲突后的前14个较强组合。`pot_bb=1.6,to_call_bb=1,stack_bb=1,iterations=2000` 时真实权益10/24=41.67%，跟注所需38.46%，EV=+0.08333BB，但求解输出 **fold=96.7271%、call=3.2729%**。

### 05 占位牌与结算

定位：`backend/table.py:108`、`:195`、`:223`、`:251`；`frontend/app.js:84`。

6 人桌英雄 BTN/AsAd，UTG 跟注、其余非 BB 玩家弃牌、BB 过牌，发翻牌前视图已有 **13 张 taken**，其中包含未知对手占位牌与烧牌。BB 占位牌含 Kh；输入 `[Kh, 合法牌, 合法牌]` 会报“牌 Kh 已不在牌堆里”。最终 revealed/payoffs 也使用 dealt 的占位牌，因此“筹码守恒”只能证明虚拟局结算一致，不能证明真实牌谱结果正确。

### 06 多家权益与边池

定位：`backend/equity.py:143`、`backend/decision.py:297`、`:474`。

皇家同花顺公共牌 AsKsQsJsTs，英雄 2c3d、对手 4c5d 与 6c7d，精确枚举返回 win=0、tie=100。上层 `win + tie/2` 得到 50%，真实主池份额为 33.333%。应分别保留“发生平局概率”和“分池权益”。

另一例：100/200 无 ante，UTG 10000 全下、HJ 10000 跟注，CO 1000 待行动，视图 pot=20300、to_call=1000，输出 required_eq=4.69%。其中大部分是 CO 无权赢取的边池。若后面 BTN/SB/BB 均弃，CO 跟注后可争夺的主池仅 3300，门槛为 30.30%。本轮用 20% 权益替身隔离公式，现实现报 EV=+3260，实际在该后续分支为 0.2*3300-1000=-340。

### 07、08 画像与范围

`backend/decision.py:151` 遍历所有 operation 而不区分街。实测 BB 翻前 check 后 intel 为 pending，翻牌下注后变成 `{line:'rfi', kind:'open'}`。

`backend/decision.py:241` 的数字牌使用倒序索引计算点数；实测 `_chen_score(('2c','2d'))=14`、99=7、TT=6。此评分进入 `:257` 的强度排序，影响“紧对手”的保留范围。

## 更值得优化的设计

### 1. 明确真实牌谱与模拟牌局的领域边界

把手牌表示为 known/unknown；把结算状态表示为 confirmed/unresolved/simulated。系统不能把为了驱动状态机临时生成的牌当成真实观察。真实牌谱允许任意与已知牌不冲突的公共牌，收益只有在信息充分时才确认为事实。该边界应先于继续做自动牌谱导入。

### 2. 建立一份不可变的分析输入

建议构造 AnalysisContext，包含手牌版本、当前街、已知死牌、座位当前投入/剩余筹码、合法动作、可赢取的底池、推断范围和推断来源。当前 `decision.py:440` 收窄范围后，`:491` 又从静态图重建 villain_merged，导致权益与 RA/NA/CFR 不一定使用同一对手模型。一次构造后共享，能减少结果相互矛盾。

输出同时区分 showdown equity、实现权益假设、chip EV、ICM 奖金期望、启发式频率和抽象 CFR 频率。NA 目前是“两对以上占比”的代理指标，不能直接解释为真实坚果占比；建议改成反映代理含义的名称。河牌范围封顶、分桶和受限下注树下，也应表述为“抽象单街模型参考”，而不是完整真实德州的精确均衡。

### 3. 前端用明确状态迁移与请求协调

继续使用原生 JS，提取小型 reducer/状态迁移模块、API 请求协调模块、渲染模块即可。让开始一手、改变设置、选择牌、提交动作、撤销、记录成功都有单一入口；取消分散的 state 字段清空逻辑。分析结果必须绑定请求提交时的 hand_id/revision。加载、失败、过期和不可计算需要显式状态。

### 4. 将学习数据变成独立持久化模型

运行数据不应作为受版本控制的 `backend/data/opponents.json` 与代码一起发布。优先考虑 SQLite 事务、hand_id 唯一约束、schema version、显式数据目录与备份导出。现有 threading.Lock 只保护本进程 record，reset 不走同一锁，固定 `.json.tmp` 在并发写/多 worker 下存在竞争；`_load` 解析失败静默回空数据也可能掩盖损坏。

画像名称应作为数据字段，不能直接占用 `_seen`、`_pool_pos` 等存储元数据键。统计应区分“手数”和“有机会做该动作的次数”；当前位置池以所有 hands 为分母，不等同于机会条件下的 RFI/3bet 率。稀疏样本建议回退人群先验并展示样本量，而非把 5 手当作稳定画像。

### 5. 用契约测试连接已有单元测试

新增测试优先级：完整 record API；两手连续学习；建议乱序响应；view 503 保留历史；合法未知公共牌；短码边池 EV；多人平分；混合 CFR 桶；全下与不同 SPR 的合法动作；范围冲突可终止；跨进程固定 seed。

CI 锁定依赖版本并保留升级验证流程。测试不要只检查频率和为 100、筹码守恒、对象字段存在；要检查输出的业务含义和独立数学基准。特别是实际适配层与通用算法之间的契约，不能用算法锚点测试代替。
