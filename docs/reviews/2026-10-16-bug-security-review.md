## 逐项证据与验收要求

### 81：结束本桌清掉已输入的真实结果

定位：[session.js](../../frontend/session.js#L441)、[app.js](../../frontend/app.js#L1512)。`endSession`直接设为ended并将settlementDraft设为null，既不提交当前草稿，也不生成当前手摘要。确认框只说保留“已确认”的余额与记录，没有说明正在输入的实际余额会被放弃；结束后的状态栏又称旧余额为“最终”余额。

真实浏览器路径：建6人桌，自己初始10000 → “弃牌并核对” → 自己实际余额填9000 → 高级区结束本桌并确认。结果为 `persistedFinal=10000`、`settlementDraft=null`、`recentHands.length=0`，状态栏“你最终10,000筹码”。[截图](../screenshots/review-2026-10-16/end-discards-real-balance.png)。

建议将结算提交拆成“提交结果”和“是否生成下一手”，结束也复用提交结果的校验/保存事务。结束时遇到未知余额，可继续使用明确标记的估算或保留待核对状态。若用户选择放弃，明确列出当前手尚未保存，且不能据此生成真实胜负统计。

验收：ready/playing/settling三种入口都覆盖；刚修改实际余额后结束，余额和本手摘要持久化正确；保存失败仍可导出并重试；取消结束不丢草稿。

### 82：错误提示提供了实际无法点击的恢复操作

定位：[app.js](../../frontend/app.js#L795) `commitSettlement`，同文件426行恢复view的onAccept，以及896–897行DOM的inert状态设置。

根因：提交期间恢复view触发renderAll，把牌桌布局和页头设为inert。提交失败后finally只把`rt.committing`置false并更新提交按钮，不执行解除inert的渲染。按钮的disabled已是false，但父级inert仍是true。

确定性复现：恢复未完成结算 → 暂缓view响应 → 提交结算并暂缓prepare → 先放行view → 再放行prepare，同时注入localStorage配额写入失败。结果 `layoutInert=true`、`headerInert=true`、`retryButtonDisabled=false`，页面提示“请导出备份后重试”，两条路径都无法点击。[截图](../screenshots/review-2026-10-16/settlement-failure-leaves-page-inert.png)。已有核心浏览器回归也在保存失败恢复环节超时，[失败日志](../screenshots/review-2026-10-16/core/failure.json)。

建议把页面交互锁放到统一函数，finally无条件同步DOM与内存锁状态。避免错误处理依赖一次全量渲染才能解锁，也不能通过清空草稿解决。

验收：控制view/prepare两种完成顺序，组合保存配额失败、HTTP503、超时；失败后输入、导出、纠正及重试可用，没有追加手数或重复扣盲注。

### 83：当前手号被当成累计完成数量

定位：[app.js](../../frontend/app.js#L955)。状态栏直接显示session.handNumber。快捷弃牌已完成第一手后自动准备第二手，此时结束便显示“共2手”。[截图](../screenshots/review-2026-10-16/end-count-off-by-one.png)。

建议增加持久化累计完成数量，只随确认提交增长；当前手是否放弃、是否只生成待开始占位，应有明确口径。历史摘要窗口只有100手，不能用数组长度修补累计数量。

验收：0手、1手、101手以上；开始即结束、生成下一手后结束、当前手未结算即结束；页面和导出统计一致。

### 84：check与call语义混同

定位：[table.py](../../backend/table.py#L203)。两个动作都调用`state.check_or_call()`，没有检查用户请求的动作是否匹配需要跟注的金额。

隔离API场景：BTN6、SB1=100、BB2=200，3号位面对200，传`type=check`。响应200，3号筹码10000变9800，底池500。当前界面通常按合法按钮提交，**本项没有证明普通界面点击过牌也会扣款**；问题存在于后端动作契约，错误调用或导入的“过牌”会成为付费跟注。

验收：无需跟注时check成功，面对下注时check明确4xx；allin/raise/fold语义不受影响，原确认动作不被回滚。

### 85：allin只走加注分支

定位：[table.py](../../backend/table.py#L224)。代码无条件调用`complete_bet_or_raise_to`。当剩余筹码不足以跟足时，正确操作应是全下跟注，并不具备加注金额。

隔离API场景：自己5号位仅300，3号raise到1000、4号fold，此时自己allin返回400，改成call返回200。**当前UI会给出跟注入口，本项不是“短码在界面完全无法跟注”。**

验收：筹码低于/等于跟注金额、完整加注、未达最小加注的短全下、加注权未重开的多方场景；合法全下金额、边池及后续行动权正确。

### 86：API与内部权益引擎对同一输入给出不同含义

定位：[app.py](../../backend/app.py#L20) `VillainIn`缺少weights，Pydantic默认忽略额外字段；内部[权益引擎](../../backend/equity.py)支持权重。

复现：hero AsAh，对手组合KhKd与2c2d，weights=[1,0]，河牌Kc7d8h9sJc，1000次、seed42。内部按权重结果0%；公开API按等权结果52%。这是输入被变更，不是普通蒙特卡洛波动。

当前牌桌默认请求未使用该权重字段，不能据此断言所有默认建议均错误。如果产品决定不开放权重，明确拒绝也可以；不要200返回另一种含义的结果。

验收：模型接受权重后验证长度、有限非负、总和大于0；全零/负值/NaN/不等长返回4xx；API与内部同种子结果一致。

### 87：单项有限不保证总额有限

定位：[table_context.py](../../backend/table_context.py#L142)、[app.py](../../backend/app.py#L344)。`[1e308,1e308]`每项都有限，prepare返回200，但总奖金无穷大导致view输出不可序列化值并返回500。`[10**400]`作为JSON整数会在`math.isfinite`转换时OverflowError，prepare直接500。

这是构造异常请求才能触发的输入健壮性问题，**没有证明一次请求导致整个服务退出**。应给业务金额合理上限，并验证转换过程与sum结果。仅在路由外围吞异常会隐藏问题，不能代替统一输入规则。

验收：极大整数、有限项求和溢出、NaN/Infinity、全零、负数、错误名次顺序；所有入口4xx一致，正常奖金计算不变。

### 88：已修复的15秒保护未覆盖advice

定位：[request-coordinator.js](../../frontend/request-coordinator.js#L107)。view有超时，submitAdvice仅创建AbortController，没有截止时间。

真实浏览器暂缓advice请求16.5秒，`aria-busy=true`、文本“正在推演…”且没有retry-advice按钮。[截图](../screenshots/review-2026-10-16/advice-stall-no-retry.png)。根据代码，只要连接一直不结束就不会进入错误恢复路径；16.5秒是本次观测窗口，并非推演应在此时间内完成的性能承诺。

建议按实际计算预算给推演单独配置超时，展示可理解的等待状态，允许取消/重试。浏览器abort不保证服务端CPU计算立即终止；计算预算和并发准入应在服务端处理。不能为了修复超时擅自减少用户采样次数。

验收：永不返回、非JSON错误、HTTP503、取消后迟到响应、换手后返回；按钮和busy状态恢复，旧结果不会写入新手。

### 89：管理员清空没有参与同一把锁

定位：[opponents.py](../../backend/opponents.py#L229)。record_hand/reset_user使用_LOCK，reset_all直接_save({})。

确定性线程测试使用临时文件：记录线程读取包含old用户的数据，在写入前暂停且持有_LOCK → 主线程执行reset_all成功，文件确实为{} → 记录线程恢复保存 → old用户及其历史重新出现。它是并发一致性问题，**不是全局管理员令牌被绕过**。

验收：清空完成后的历史不能被先前读到的快照恢复；并发记录/用户重置/全局重置可串行化。若部署多worker，threading.Lock仍不足，需跨进程锁或SQLite事务；不能仅给reset_all加线程锁就宣称多进程安全。

## 建议的设计调整及修复顺序

1. **结算、结束和保存共用事务边界。** 正式余额、手摘要、累计计数应一同成功或一同保留草稿，结束本桌不另走一套简单清空逻辑。
2. **异步状态与DOM锁统一管理。** 用一个出口处理请求完成/失败/取消，避免内存已解锁但页面仍inert；补受控响应顺序的测试。
3. **动作与数值校验集中到接口边界。** check/call/allin保留明确语义，prepare/view/advice共享金额和ICM验证；模型不要默默丢弃影响计算含义的字段。
4. **正式统计与学习样本分开。** 用户场次、真实手数、估算余额、画像样本、有效模拟次数不是同一个计数。账户版本应先定义清楚再接图表。
5. **公开服务补齐认证、存储和计算预算。** 优先采用现有FastAPI加SQLite事务，无需为了这些问题整体重写前端或引入微服务。

建议批次：先81/82及R1/R2，再83–87/89，最后88与计算任务管理一起实施；R3/R4在显示统计或账户上线前完成。修复时先把本轮缺陷复现脚本改成正确行为断言，再进入正式回归，不能把“成功复现缺陷”的退出0当成修复通过。
